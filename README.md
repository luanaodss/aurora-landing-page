# Aurora — Landing Page (Enterprise Challenge, Etapa 1)

Landing page B2B para a **Aurora**, startup de RH as a Service, desenvolvida como projeto acadêmico do Enterprise Challenge.

Este projeto **não cria uma nova marca**: evolui a experiência digital da Aurora a partir da identidade, posicionamento e conteúdo já existentes no site oficial ([aurorapro.com.br](https://aurorapro.com.br/)).

## Como rodar localmente

A página funciona abrindo `index.html` diretamente no navegador (ou servindo a pasta com qualquer servidor estático) — o CSS do Tailwind já vem **compilado** em `css/tailwind.css`, então isso não exige Node nem build:

```bash
npx serve .
# ou
python3 -m http.server 8000
```

Só é preciso rodar um build se **alterar classes do Tailwind no HTML** (ver seção "Tecnologias"):

```bash
npm install
npm run build:css
```

## Estrutura de pastas

```
/aurora
  /assets/images       → logo oficial da Aurora
  /css
    tailwind.css       → CSS compilado (commitado — abrir o site não exige build)
  /js

  /src
    input.css          → fonte do Tailwind (@tailwind + tokens de marca + componentes)

  index.html
  README.md
```

## Tecnologias

HTML5 semântico, **Tailwind CSS** (utilitário, compilado via CLI — sem PostCSS/bundler adicional) e JavaScript vanilla. Ícones da biblioteca **Lucide**, usados como SVG inline (sem carregar o runtime JS da Lucide) — mesma aparência visual, porém sem dependência de JavaScript para renderizar ícones, o que é melhor para performance e para leitores de tela (o ícone já existe no HTML, não depende de script rodar).

Por que Tailwind: a pedido do grupo, para acelerar iteração visual e manter consistência de espaçamento/cor via tokens de marca configurados em `tailwind.config.js`. Trade-off documentado: usamos o Tailwind CLI standalone (sem framework de build tipo Vite/Webpack) para manter a promessa da Etapa 1 de "abrir e funcionar" — o CSS final já vem compilado e commitado no repositório.

## Decisões de design (para justificativa acadêmica)

- **Arquitetura de seções**: Header → Hero → Problema → **Diagnóstico rápido** (interativo) → Solução/Sobre → RH as a Service (produto) → Como Funciona (motor de inteligência) → Depoimentos → Planos → Formulário de contato → Footer. A ordem resolve uma ambiguidade do site original, que misturava três narrativas (plataforma, IA, dor do desligamento) sem hierarquia clara — a página abre com a tensão emocional real (decisões difíceis sobre pessoas), deixa o visitante se autoavaliar, evolui para a amplitude do produto, mostra a plataforma em uso e fecha com a resolução via IA (Chatbot Boreal).
- **Seção "Funcionalidades" ("Na prática") — implementada e depois removida**: o Briefing Completo oficial marcava como pendente um mockup real da plataforma no Hero e/ou em uma seção de funcionalidades. A Aurora forneceu 8 capturas de tela reais da plataforma, e essa seção passou por 3 rodadas de redesenho: (1) 2 telas fictícias recriadas em HTML/CSS, por precaução com dados sensíveis; (2) os 2 prints reais correspondentes (Feedbacks + Chatbot Boreal) lado a lado, dentro de uma moldura "janela de navegador"; (3) 1 único print real (Feedbacks) em destaque, com 2 marcadores numerados (círculos com a cor de marca) apontando elementos específicos da tela, explicados ao lado em uma lista real. Essa versão 3 foi testada e documentada como correta, mas um teste posterior (screenshot automatizado em várias larguras) revelou que os círculos numerados estavam, de fato, cobrindo texto real da captura (a nota do feedback, o texto "a melhorar") — a calibração "pixel a pixel" registrada numa rodada anterior não correspondia mais ao resultado renderizado. Antes de corrigir a calibração, uma análise da imagem-fonte mostrou a causa raiz: a tela de Feedbacks é densa (dois cards cheios de texto, quase sem área vazia), então qualquer marcador numerado ali teria pouco espaço seguro para pousar sem sobrepor algum texto — não era um erro pontual de coordenada, era um descompasso estrutural entre a técnica escolhida (pino numerado sobre print cheio) e essa imagem específica. Avaliadas 3 alternativas (recalibrar os círculos; trocar por 2 recortes menores e focados, um por callout; trocar o círculo preenchido por um contorno vazado), Luana optou por **remover a seção inteira**, em vez de aplicar qualquer correção. A seção foi removida do HTML (incluindo o CSS `.callout-marker`/`.callout-marker-inline`, que ficou sem uso), sem deixar espaçamento residual entre "RH as a Service" e "Como Funciona" (testado com screenshot da transição entre as duas seções). O Chatbot Boreal, que também aparecia nessa parte da página em rodadas anteriores, não perde espaço: continua com destaque próprio na etapa 5 do "Motor de Inteligência" (badge "Chatbot Boreal") e no cluster Ação & Inteligência de "RH as a Service".
- **Hero com mockup real + "glow" de marca**: o triângulo abstrato com gradiente que ocupava o Hero foi substituído por um **print real da plataforma** (cards "Minhas Metas" e "Alinhamento Cultural"), a pedido de Luana — mesmo critério do briefing de priorizar mockup real do produto. O gradiente de marca (teal → rosa → violeta) que antes preenchia o triângulo foi mantido, mas como um "glow" decorativo desfocado atrás do card (puramente `aria-hidden`), preservando a identidade cromática da marca no Hero sem inventar uma nova. **Trade-off assumido conscientemente**: as cores de UI do print real (o amarelo do anel de metas, o violeta do gráfico radar) não fazem parte da paleta de 4 cores de marketing da marca — diferente de um mockup ilustrado, um print real não dá para "recolorir" sem deixar de ser real. Luana avaliou essa mistura de paleta e optou por manter o print real mesmo assim, priorizando autenticidade de produto sobre pureza cromática — decisão registrada aqui para constar na defesa do projeto.
- **Hero — print "em evidência" (sangrando a viewport)**: numa segunda rodada, Luana achou a primeira versão do mockup do Hero pequena/contida demais e pediu para deixá-lo em evidência, no padrão comum de hero de SaaS onde o print do produto é grande e sangra para fora da tela (referência visual enviada por ela). Em telas médias/grandes, o card do print escapa do grid de texto via `position:absolute` e se estende até (e um pouco além) da borda direita da viewport, cortado pelo `overflow-hidden` da section — o texto fica limitado a ~42% da largura para nunca sobrepor o print (testado em 390/768/1024/1280/1440/1920px, sem sobreposição em nenhuma). Em mobile, sem espaço de sobra pra sangrar, ele volta ao fluxo normal, contido, abaixo do texto.
- **Hero — troca para o print de "Meu Painel" (visão do gestor), sem recorte**: numa terceira rodada, Luana enviou um print novo (o painel do gestor, com Termômetro da Equipe, Foco de Atenção, Gestão Contínua) e pediu para usá-lo **sem cortar** — a tela inteira, sidebar e cabeçalho inclusos, não só um recorte de cards — e para tirar o "glow" gradiente que ficava atrás do card. Os dois pedidos foram atendidos: a imagem é o print completo (só redimensionado, não recortado) e o `<div>` decorativo do gradiente foi removido do Hero. **Trade-off a observar**: por ser uma tela cheia de dashboard (bem mais densa que os 2 cards recortados da versão anterior), a legibilidade no mobile é menor — nesse tamanho o print funciona mais como "prova de que é produto real" do que como conteúdo para ler em detalhe; em telas médias/grandes (onde o print aparece bem maior, sangrando a viewport) ele é perfeitamente legível.
- **Hero — proporção 50/50 e menos linhas no título**: com o print completo do painel ocupando ~64% da largura da section, Luana achou que ele estava dominando demais e pediu para reduzir para 50%. Isso liberou espaço horizontal, então a coluna de texto também foi alargada (de ~42% para ~52-54% da largura do container) — o título quebra em menos linhas sem precisar reduzir o tamanho da fonte (`text-5xl`/`text-6xl` mantidos). Testado em 1024/1280/1440/1920px, sem sobreposição.
- **Hero — espaçamento vertical reduzido para caber "acima da dobra"**: o padding vertical da section e as alturas mínimas (`min-h`) eram generosos o bastante para empurrar o final do Hero (botões de CTA) para fora da área visível em janelas de navegador comuns (larguras grandes, mas altura útil menor por causa de barra de abas/favoritos do navegador). Reduzimos o padding (`py-24`→`py-12` em telas médias/grandes) e as alturas mínimas da section/container (660px/620px → 520px/480px) — o Hero inteiro (título + texto + CTAs + print) agora cabe em ~636px de altura, contra os ~812px de antes. Verificado que o print (com sua altura própria, decorrente da proporção 50% de largura) continua sempre menor que a altura da section em todas as larguras testadas, então nada é cortado pelo `overflow-hidden` — só o espaço "vazio" ao redor foi comprimido.
- **Espaçamento entre seções reduzido, na grade de 8px**: todas as seções de conteúdo (Problema, Diagnóstico, Solução, RH as a Service, Funcionalidades, Como Funciona, Depoimentos, Planos, Contato) usavam `py-16 md:py-24` (64px/96px de respiro vertical, em cima e embaixo de cada uma) — Luana achou o espaço entre seções grande demais. Padronizado para `py-12 md:py-16` (48px/64px), ambos múltiplos de 8px como o restante da escala do Tailwind já usa. O rodapé teve o mesmo tratamento (`pt-14`/`mt-16` → `pt-12`/`mt-12`). O Hero mantém seu próprio espaçamento (já reduzido numa rodada anterior, para caber acima da dobra) — não foi tocado aqui.
- **Dois casos reais de "texto quebrando linha por falta de espaço, não por excesso de texto"**: (1) o menu do cabeçalho virava para o layout "desktop" (todos os links + botão numa linha só) a partir de 768px, mas nessa largura específica o conjunto de links + botão não cabia mais numa linha só — "Como funciona" e "Agendar demonstração" quebravam ao meio de forma feia. Causa: o breakpoint de troca (`md`, 768px) era estreito demais para caber tudo numa linha. Corrigido adiando a troca para `lg` (1024px) — entre 768 e 1023px o site agora usa o menu mobile (hambúrguer), que tem espaço de sobra, e o menu horizontal só aparece quando cabe confortavelmente. (2) os 3 "pilares de valor" da seção "A Solução" (Dados centralizados / Consciência humana / Decisão com IA) ficavam sempre em 3 colunas a partir de 640px, e em telas por volta de 768px essas colunas ficavam estreitas demais, forçando títulos como "Dados centralizados" a quebrar palavra por palavra. Corrigido: 2 colunas entre 640-1023px, 3 colunas só a partir de 1024px, onde já há espaço de verdade. Ambos verificados em 768/834/1000/1023/1024/1280px.
- **Revisão de copy: menos travessão (—), mais pontuação natural**: um padrão de escrita comum em texto gerado por IA é o uso frequente do travessão para encaixar uma ideia extra no meio da frase. Passamos por todo o texto visível da página (títulos, parágrafos, itens de lista, `aria-label`, depoimentos, e os textos de resultado do diagnóstico gerados por JS) trocando cada ocorrência por pontuação mais natural em português: vírgula quando é uma ideia complementar dentro da frase, dois-pontos quando introduz uma explicação ou é o separador de um item com termo em negrito (ex.: "Ciclo de Performance: acompanhe..." em vez de "Ciclo de Performance — acompanhe..."), ou frases separadas quando fazia mais sentido. As citações de depoimentos (ex.: "Natalia — Gerente de RH") viraram "Natalia, Gerente de RH", formato padrão de atribuição jornalística. Não mexemos em comentários de código (não são visíveis para quem usa o site) nem no traço curto usado em palavras compostas ("Co-CEO").
- **Seção "Planos"** foi reduzida a uma menção com CTA para a lista de espera, em vez da tabela completa de preços do site original — para manter o foco da página na proposta de valor e no formulário de lead. A tabela completa pode ser reincorporada se o grupo preferir.
- **Depoimentos reordenados**: abrem com relatos de clientes em potencial (não das fundadoras), por terem mais peso de prova social de terceiros.
- **Depoimentos em vitrine horizontal (arrastar/scroll), não em carrossel automático**: o padrão anterior (grid estático 2×2) foi substituído por uma faixa com `scroll-snap` nativo do CSS — o usuário arrasta (mouse), desliza (touch) ou usa os botões/teclado para navegar entre os 4 depoimentos. Decisão deliberada de **não** usar um carrossel com autoplay (o padrão mais comum hoje em landing pages): com apenas 4 depoimentos reais (nenhum inventado para "encher" um loop), um carrossel automático se repetiria rápido demais, e movimento contínuo sem controle do usuário fere WCAG 2.2.2 (Pause, Stop, Hide) — exigiria um botão de pausar que o autoplay por si só não justifica aqui. A vitrine com scroll manual entrega a sensação "orgânica"/moderna pedida sem esse risco.
- **"RH as a Service" e "Motor de Inteligência" — mesmo texto do site original, apresentação redesenhada**: conferimos diretamente no site oficial que não existe uma versão "mais detalhada" desse conteúdo (nenhuma página por módulo, sem accordion/"saiba mais") — cada módulo e cada etapa do motor já tinha, no original, exatamente uma frase curta, e é isso que a página reaproveita. O que evoluiu foi a apresentação: (1) uma fileira de chips coloridos acima dos 4 clusters de módulos deixa a pessoa "ir direto" a um cluster (mesma interação de clicar-e-destacar já usada nos módulos recomendados do diagnóstico — reforça consistência, um dos heurísticos de Nielsen); (2) o motor de inteligência ganhou uma linha vertical que conecta as 5 etapas e "acende" progressivamente conforme a rolagem, reforçando que é uma engrenagem sequencial (uma etapa alimenta a próxima) e não 5 recursos soltos.
- **"O Problema" — de lista de texto a mini-cards com ícone**: os 3 pontos de dor (dados espalhados, decisão sob pressão, pouca visibilidade) eram uma lista com marcador colorido; viraram 3 cards com ícone Lucide, mesma linguagem visual usada no resto da página — resolve o "bloco de texto monótono" sem adicionar nenhuma informação nova. **Ajuste posterior**: o parágrafo de apoio, logo acima dos 3 cards, tinha uma largura máxima em caracteres (`max-w-[62ch]`) que fazia a linha de texto parecer bem mais curta que a fileira de cards logo abaixo — inconsistente visualmente. Removido o limite: o parágrafo agora ocupa a mesma largura da fileira de cards.
- **"A Solução" — layout em duas colunas, fundadoras como cards de foto**: a versão original empilhava tudo em coluna única (eyebrow, título, parágrafo, 3 pilares de valor, e por fim as fundadoras lado a lado, cada uma num card horizontal com avatar redondo). A pedido de Luana (com um esboço marcando onde as fundadoras deveriam ficar), a seção virou duas colunas a partir de 1024px: **à esquerda**, o conteúdo institucional (eyebrow, título, parágrafo e os 3 pilares de valor); **à direita**, as duas fundadoras lado a lado, redesenhadas como cards de foto vertical (retrato em `aspect-ratio` 4:5 preenchendo a largura do card, nome e cargo centralizados abaixo) em vez do avatar redondo horizontal anterior — o rótulo "Cargo" foi simplificado de "Sócia Fundadora e Co-CEO" para só "Co-CEO" (o card já está sob o rótulo "Fundadoras", então repetir "Sócia Fundadora" era redundante, e o texto completo quebrava de forma feia na coluna mais estreita). Abaixo de 1024px a seção volta a empilhar em coluna única, na mesma ordem de antes. O link real para o LinkedIn de cada fundadora e o efeito de hover/foco acessível (`group-focus-within`) foram mantidos sem alteração — só o card interno mudou de forma.
- **Pilares de valor da "A Solução" — de lista vertical a grade horizontal**: numa primeira versão do layout de duas colunas, os 3 pilares (Dados centralizados / Consciência humana / Decisão com IA) ficaram empilhados em coluna única, cada um com ícone à esquerda do texto — solução defensiva pensada para não repetir o bug de quebra de palavra já corrigido numa rodada anterior. Luana notou que isso deixava muito espaço horizontal vazio à direita da coluna (entre o texto dos pilares e os cards das fundadoras) e pediu para os pilares ficarem alinhados na horizontal, usando todo o espaço disponível. Reestruturado para uma grade de 3 colunas (`grid-cols-3` a partir de `sm`, 640px), com cada ícone agora **acima** do título e do texto (em vez de ao lado) — isso dá a largura inteira da coluna para o texto quebrar, em vez de dividir essa largura entre ícone e texto lado a lado. Testado em 390/640/768/1024/1280/1440px: abaixo de 640px os pilares voltam a empilhar em coluna única (não há largura suficiente para 3 colunas legíveis nesse tamanho); a partir de 640px, os títulos quebram no máximo em 2 linhas, sempre em espaço entre palavras (nunca no meio de uma palavra), e a partir de ~1130px (largura máxima do container) cada título cabe numa linha só. Sem overflow horizontal em nenhuma largura testada.
- **"O seu RH as a Service" — parágrafo e chips de cluster em largura total**: mesmo padrão de bug já visto em "O Problema" (ver acima): o parágrafo logo abaixo do título tinha `max-w-[68ch]`, deixando-o visivelmente mais curto que os chips de cluster e o grid de cards logo abaixo. Removido o limite. Os 4 chips de cluster (Performance & Metas, Cultura & Valores, Escuta & Dados, Ação & Inteligência) formavam uma fileira `flex flex-wrap` que, tecnicamente, já ocupava a largura inteira do container, mas cada chip só tinha a largura do próprio texto, deixando bastante espaço vazio à direita do último chip. Luana pediu para os chips também preencherem o espaço, então a fileira virou uma grade (`grid`) de colunas iguais, com cada chip esticado (`w-full justify-center`) para preencher sua célula: 1 coluna no mobile (cada chip em largura total, empilhados), 2 colunas a partir de 640px, 4 colunas (uma fileira só) a partir de 1024px. Os breakpoints foram escolhidos medindo o rótulo mais longo ("Ação & Inteligência"): 2 colunas exigiria menos de ~190px por chip para não quebrar linha dentro do formato de pílula, o que só é seguro a partir de 640px, por isso o mobile fica em 1 coluna em vez de 2. Testado em 390/640/768/1024/1440px sem quebra de linha dentro de nenhum chip e sem overflow horizontal; confirmado por teste automatizado que os chips continuam focáveis por teclado e que o clique ainda rola até o cluster certo e aplica o anel de destaque (a função `scrollToAndHighlight` não foi alterada, só o CSS do contêiner e dos próprios links).
- **Formulário de contato centralizado**: a seção final ("Protagonize o fenômeno na sua empresa") tinha o bloco inteiro (eyebrow, título, texto e formulário) alinhado à esquerda dentro do container de 760px, sem `mx-auto` — em telas largas, isso deixava bastante espaço vazio à direita, um desalinhamento visual perceptível bem no fechamento da página. Adicionado `mx-auto` ao bloco de 760px, centralizando-o no container. Eyebrow, título e texto de apoio passaram a ser centralizados (`text-center` num wrapper próprio, sem afetar o formulário); os campos do formulário em si (labels, inputs, botão) continuam alinhados à esquerda dentro do bloco centralizado — centralizar texto de rótulo/formulário prejudicaria a leitura e destoaria do resto do site, então mantivemos esse padrão. Testado em 390/768/1024/1440px, sem overflow horizontal.
- **Sem dados inventados**: nenhum número, cliente, funcionalidade ou depoimento foi criado. Onde a informação real não estava disponível, isso está sinalizado no próprio conteúdo/documentação como `INFORMAÇÃO A VALIDAR` (hoje, só o RM dos integrantes).

## O elemento disruptivo: Diagnóstico Rápido

O critério de avaliação "solução disruptiva" foi resolvido com um **diagnóstico interativo de 3 perguntas**, 100% client-side (sem backend), posicionado logo após a seção "O Problema". Três ideias foram avaliadas antes de decidir:

1. **Diagnóstico rápido** (escolhida) — 3 perguntas sobre como a empresa decide hoje sobre pessoas, com resultado personalizado e CTA que já leva a resposta sobre porte da empresa para o formulário de lead (progressive profiling). Viável para o prazo (sem backend), reforça a proposta de valor da própria Aurora (dados > achismo) e ainda ajuda a qualificar o lead.
2. Visualização animada do motor de inteligência (grafo de dados conectando os 5 componentes) — visualmente forte, mas mais complexa de construir bem e menos "útil" para quem visita.
3. Slider "antes/depois" (dados dispersos vs. visão consolidada) — simples de construir, mas mais decorativo, menos alinhado à proposta de conversão.

A opção 1 foi recomendada e implementada por unir três coisas ao mesmo tempo: reforça a mensagem central da marca, gera engajamento real (não é só uma animação) e ainda alimenta o formulário de contato.

**Resultado direcionado, não genérico.** A primeira versão calculava só um placar (0–4) e mostrava uma de 3 mensagens genéricas. Evoluímos para um **diagnóstico de 2 eixos** — maturidade do *processo de decisão* (pergunta 1) e maturidade da *consolidação de dados* (pergunta 2) — que gera 5 perfis diferentes, cada um recomendando **módulos reais da Aurora** (não uma frase motivacional):

| Perfil | Eixo mais fraco | Módulos recomendados |
|---|---|---|
| Decisões no escuro | os dois | Radar de Experiência + Ciclo de Performance |
| Dados sem direção | processo de decisão | Chatbot Boreal + Planos de Ação |
| Faltam dados para sustentar | consolidação de dados | Radar de Experiência + Pesquisas Customizáveis |
| Meio caminho andado | nenhum (empate) | Feedbacks Contínuos + Avaliação de Valores |
| Prontos para escalar | nenhum (os dois altos) | Chatbot Boreal + Planos de Ação |

Cada módulo recomendado é um link clicável que rola até o card correspondente em "RH as a Service" e o destaca com um anel temporário (2,2s) — o diagnóstico não só recomenda em texto, ele **aponta fisicamente** para a parte da página que resolve aquele problema.

## Recursos de acessibilidade implementados

- **HTML semântico**: `header`, `nav`, `main`, `section`, `blockquote`/`cite`, `fieldset`/`legend`, `footer`, um único `h1` por página e hierarquia correta de `h2`/`h3`.
- **Skip link**: primeiro elemento focável da página, permite pular direto para o conteúdo principal.
- **Foco visível**: outline customizado (`outline: 3px solid teal`) em todos os elementos interativos — nunca removido via `outline: none`.
- **Navegação por teclado**: menu mobile controlado por `button` nativo com `aria-expanded`/`aria-controls`, fecha com `Esc` e ao ativar um link. Âncoras internas (`#solucao`, `#contato` etc.) usam `scroll-margin-top` para não ficarem escondidas atrás do cabeçalho fixo.
- **Diagnóstico interativo acessível**: cada pergunta é um `<fieldset>`/`<legend>` com `<input type="radio">` nativos (não `<div>`s clicáveis) — funciona nativamente com teclado e leitor de tela; ao avançar de etapa, o foco é movido programaticamente para o título da próxima pergunta, para quem usa leitor de tela acompanhar a mudança de contexto; validação impede avançar sem selecionar uma opção, com mensagem `role="alert"`.
- **Formulário de lead acessível**: `label` associado a cada campo, indicação de obrigatoriedade textual (não só por cor), mensagens de erro com `role="alert"` e `aria-describedby`, mensagem de sucesso com `role="status"`/`aria-live="polite"`.
- **Honeypot acessível**: campo anti-spam escondido via posicionamento fora da tela (não `display:none`) e `aria-hidden="true"` + `tabindex="-1"`, para não ser alcançado por navegação de teclado nem lido por leitor de tela.
- **Contraste de texto**: a cor `muted` original da marca (`#8a87a0`) rende ~3.5:1 em fundo claro — insuficiente para texto normal (WCAG AA exige 4.5:1). Foi criada uma variação mais escura (`#6b6884`, ~5.3:1) para uso em texto corrido, reservando a cor original apenas para elementos grandes/decorativos.
- **Área de toque**: botões e campos com `min-height: 44px`.
- **`prefers-reduced-motion`**: rolagem suave, transições, a animação flutuante do hero e a revelação de seções ao rolar são todas desativadas para quem configurou redução de movimento no sistema — e a revelação ao rolar só é aplicada via JavaScript (progressive enhancement): sem JS, nada fica invisível.
- **Textos alternativos**: logo com `alt="Aurora"`; ícones e ilustrações puramente decorativos marcados com `aria-hidden="true"`. As fotos das fundadoras usam `alt=""` (decorativas) porque o nome já aparece como texto visível ao lado — evita anúncio duplicado em leitor de tela.
- **Vitrine de depoimentos acessível**: nada é escondido do leitor de tela — os 4 depoimentos continuam todos no HTML (uma `<ul>` normal) e são lidos em ordem, independentemente de onde o scroll horizontal está parado. Para quem usa mouse, arrastar funciona; para quem usa teclado, a faixa é focável (`tabindex`) e as setas ←/→ do teclado navegam um depoimento por vez; para quem usa mouse sem querer arrastar, há botões "anterior"/"próximo" com `aria-label` que ficam `disabled` (não só visualmente apagados, mas realmente desabilitados) ao chegar no início/fim. Por não ter autoplay, não existe conteúdo se movendo sozinho — logo não há necessidade de um botão de pausa (WCAG 2.2.2) nem risco de o leitor de tela perder uma citação que "passou" sozinha.
- **Efeito de hover acessível**: o destaque colorido/anel nas fotos das fundadoras usa `group-focus-within` além de `group-hover`, então quem navega por teclado (Tab) vê o mesmo efeito de quem usa mouse. Isso só funciona de verdade porque o card inteiro é um link (`<a>` para o LinkedIn de cada fundadora) — um elemento genuinamente focável; sem isso, `group-focus-within` nunca teria um alvo para disparar.
- **Navegação por cluster e linha de progresso acessíveis**: os chips de "RH as a Service" são links reais (`<a href="#cluster-...">`) — funcionam mesmo sem JavaScript (âncora nativa do navegador); com JavaScript, o clique passa a rolar suavemente e destacar o card. A linha de progresso do "motor de inteligência" é 100% decorativa (`aria-hidden`), não é ativada quando `prefers-reduced-motion` está ligado, e nenhum texto do motor de inteligência depende dela para ser lido.
- **Links externos identificados**: Instagram e LinkedIn no rodapé abrem em nova aba (`target="_blank"`) com `rel="noopener noreferrer"` e isso é avisado no próprio `aria-label` ("abre em nova aba"), para quem usa leitor de tela não ser surpreendido pela troca de contexto.
- **Responsividade**: layout testado em desktop, tablet e mobile, com menu de navegação adaptado para toque; verificado com testes automatizados de captura de tela durante o desenvolvimento (não fazem parte do entregável final).
- **Captura de tela sem "UI fantasma"**: a imagem do Hero é um print estático (`<img>` com `alt` descritivo, sem nenhum `<button>`/`<input>`/`<a>` reconstruído por cima) — nenhum leitor de tela ou usuário de teclado encontra um controle clicável que na verdade não faz nada (o Hero não tem mais glow decorativo — foi removido a pedido de Luana). A seção "Funcionalidades", que também tinha um print real com marcadores numerados decorativos, foi removida (ver bullet acima).

## Auditoria automatizada de acessibilidade (09/09/2026)

Antes de fechar a entrega (FASE 7/8), rodamos o [axe-core](https://github.com/dequelabs/axe-core) (mesmo motor usado pelo Lighthouse e pelas DevTools de acessibilidade do Chrome) contra a página renderizada, cobrindo as tags WCAG 2.0/2.1 A e AA, via Playwright com `prefers-reduced-motion: reduce`. Resultado antes das correções: **1 violação confirmada** + 2 alertas "revisão manual necessária" que a ferramenta não consegue decidir sozinha (fundos com gradiente). Depois das correções abaixo: **0 violações**.

**1. Badge "Chatbot Boreal" e o número "5" do último passo do motor de inteligência (confirmado pelo axe-core).** Os dois usavam texto branco sobre o fundo teal da marca (`#31b4a6`), um contraste de 2,55:1, texto pequeno em negrito, WCAG AA exige 4,5:1 para esse tamanho. Corrigido trocando a cor do texto de branco para a cor "tinta" (`#1b1733`), que sobre o mesmo teal chega a 6,75:1. Validado visualmente (screenshot antes/depois): o teal continua a cor de destaque do card, só o texto por cima ficou legível para quem tem baixa visão.

**2. Parágrafo de apoio da seção "Planos" (encontrado por verificação manual, não pelo axe-core diretamente).** O texto usava `text-white/90` (branco a 90% de opacidade) sobre um `background: linear-gradient(to bottom right, violeta, rosa)`. O axe-core sinaliza fundos com gradiente como "não verificável automaticamente", então fizemos a checagem manual: renderizamos a seção em 3 larguras (390/1024/1440px), escondemos temporariamente o texto (mantendo o layout) e amostramos, pixel a pixel, a cor de fundo real sob a área de cada bloco de texto. No canto inferior direito do parágrafo (onde o gradiente pende mais para o rosa), o contraste caía para 4,05:1 a 4,44:1 conforme a largura, abaixo do mínimo de 4,5:1. O título (`text-white`, sem opacidade, e maior/mais em negrito) e o eyebrow ficaram sempre acima de 4,9:1, então não precisaram de ajuste. Corrigido removendo a opacidade do parágrafo (`text-white/90` → `text-white`); nas mesmas amostras, o pior caso passou a 4,61:1 (mobile) a 5,09:1 (desktop), sempre acima do mínimo, com folga.

**3. Grupo de chips de "RH as a Service" (alerta técnico, sem impacto visual).** O `<div>` que agrupa os 4 chips de cluster tinha um `aria-label` para descrever o grupo, mas um `<div>` sem `role` explícito tem papel de acessibilidade "genérico", e a especificação ARIA não garante que um `aria-label` produza nome acessível nesse caso, o navegador pode simplesmente ignorá-lo. Corrigido adicionando `role="group"` ao mesmo elemento, que passa a ter um papel de acessibilidade reconhecido e o rótulo passa a ser exposto de fato a quem usa leitor de tela.

Os 2 alertas de "revisão manual" restantes (depois das correções) foram checados e são falsos positivos: os links do menu do cabeçalho usam um fundo semitransparente com `backdrop-blur` (o axe não consegue calcular com certeza o que está atrás), mas o texto é a cor "tinta", bem escura, sobre um fundo claro em qualquer cenário realista (contraste ≥16:1 mesmo no pior caso testado); e o parágrafo do 5º passo do motor de inteligência usa um gradiente entre dois tons quase brancos (`bg-tint` → `surface`), testado e confirmado acima de 7,9:1 nas duas pontas.
